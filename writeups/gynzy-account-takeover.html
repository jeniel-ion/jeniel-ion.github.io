Account Takeover via Broken Access Control — Gynzy

Found a broken access control bug in Gynzy, a platform teachers and students use for running classrooms.

Short version

  • The admin UI won't let you touch accounts you shouldn't — but the API behind it wasn't asking the same questions. I swapped the userId in an email-change request to a different student, and it just worked.
  • The server did check that the student was in my classroom. It never checked whether I was allowed to change their email.
  • Email is where password resets go. So: change the email, hit "forgot password", the reset link lands in my inbox, new password, done.
  • And it worked on every type of student in the class — not just one.

How I found it

Gynzy lets teachers manage a classroom full of student accounts. Like most apps, the restrictions live in the UI — buttons you can't click, options you can't see. That's fine for honest users, but I wanted to know whether the API enforced the same rules for someone who doesn't bother with the UI at all.

The user-management requests had the target's user ID sitting right inside them, so that's where I started poking.

The bug

I logged in as the classroom admin and replayed the email-change request, pointed at a different student:

POST /<email-update-endpoint>
...
userId=<target-user-id>
email=<attacker-controlled-email>

I changed userId from my own account to another student account I control, and the server accepted it — the email got updated as if nothing happened.

Here's the thing: the server did verify the student belonged to my classroom. So it was paying attention — it just asked the wrong question. It confirmed who this student was to me, but never asked whether I should be allowed to change their email at all. Those are two completely different permissions:

"is this student in my classroom?"        → yes, go ahead   ✓ asked
"is this admin allowed to change emails?" → never asked      ✗

Managing a classroom and resetting a student's login email are not the same thing — the code treated them like they were.

Chaining it

Changing an email doesn't hand me their password — it's just one field in a database. So I asked the obvious question: what else trusts that field?

Password recovery does. The forgot-password flow sends a reset link to whatever address is sitting on the account. And I had just made that address mine:

Admin session
     ↓
Modify target user's email
     ↓
Email becomes attacker-controlled
     ↓
Forgot Password
     ↓
Password reset delivered to attacker
     ↓
New password
     ↓
Target account compromised
